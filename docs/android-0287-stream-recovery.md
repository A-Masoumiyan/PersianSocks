# Android 0.28.7: preserve active TCP and recover the physical route

Previously, either TCP read direction timed out after 180 seconds and closed both directions. A steady download with no upload payload, or a steady upload waiting for its final response, could therefore be interrupted locally. Relays now use one last-activity clock updated by both pumps and a single bounded watchdog. Five minutes of **bidirectional inactivity** closes the stream; EOF half-closes the other socket and allows its remaining response. Explicit cancellation still closes blocked reads/writes and releases the session once.

The native maximum is now 64 sessions, matching the gateway's existing 64-session budget. The worker ceiling is derived as 3 × 64 for the most expensive UDP association; it is not an unbounded executor. Native TCP inactivity is explicitly 300000 ms, its previous default, matching the Java watchdog. No native binary is modified. Saturation reports `LOCAL_CAPACITY`; extra health probes are deferred near capacity or discarded as inconclusive if a capacity rejection occurred during sampling. The local report includes session usage, rejection count and last relay error. Existing TCP/TLS/authentication validation remains required.

A service-owned passive `NetworkCallback` observes physical INTERNET/NOT_VPN networks. Capability and link changes use callback snapshots, not synchronous queries inside callbacks. Loss of the captured route, INTERNET capability, interface or a captured source IP cancels its probes and closes its gateway. Merely adding an IPv6/privacy address preserves sockets on retained addresses. A 250 ms debounce requests reconnection to the **same proxy** using a fresh physical route, with existing bounded preflight retries; proxy failover follows only if that fails. Unrelated network loss and validation-only changes leave the active route alone. DNS-only updates expire that route's cached answers and ignore obsolete outstanding results. A separate callback Handler prevents connection cleanup from deleting framework event delivery. The callback is unregistered on service destruction. Ten-second polling remains a fallback, and disabling automatic recovery is respected.

This recovers new connections after route loss; it does not preserve an established TCP stream across a changed source IP. A working bound route is retained while other networks appear. Preferred-network migration while the old route still works is not introduced. The existing tunnel is retained during the wait; this change does not introduce an Android always-on/lockdown VPN guarantee.

## Validation

- 38 new host checks with real proxy sockets: SOCKS5/HTTP/HTTPS one-way upload and download run for 1600 ms with a 300 ms idle budget, upload half-close followed by response, both-idle cleanup, explicit cancellation, 64/65-session saturation and permit recovery, DNS-only/IP/additional-IP/interface/loss/late-old-route snapshot decisions.
- An additional simultaneous HTTP upload/download fixture passed with the production 300000 ms idle budget over 310000 ms, crossing both the old three-minute and native five-minute thresholds: 1581312 download bytes and 1580800 upload bytes. The final upload response matched every uploaded byte; both permits returned. Exact outcome is recorded in `docs/verification.txt`.
- All existing personal and Play host suites passed, including 33 Play transport checks, 38 final stream/route checks, 544 bilingual strings and the large-scan suites. Six release input checks passed. The final signed APK integrity audit passed; SHA-256 is `23914a4f0cb6e85b419060d60c42860eb8b2e640ec185fbb73cd4712644edc67`. The same approved certificate is used; versionCode is 37. One earlier rebuild was rejected by the existing missing-resource guard before signing; a fresh complete build passed the audit.

These are local host fixtures and Android compilation, not device or operator-network measurements. Android callback timing, native end-to-end traffic, Wi-Fi/cellular handover, sleep/wake, memory/thermals and real Instagram use remain to be tested on the phone. No numerical latency or throughput improvement on Tehran networks is claimed.

## Research and remaining work

This implements the stream-idle and resource-alignment portion of P0 and physical route recovery from [the network plan](android-network-stability-plan.md). Full per-stage DNS/TCP/TLS/SOCKS/HTTP timing and reply codes, per-route reliability history, selective slow retesting, adaptive scan/download load, multi-address racing, measured DNS fallback, verified UDP and evidence-driven MTU changes remain unimplemented. These are not implied by this release.

Sources reviewed: [Android network callbacks](https://developer.android.com/develop/connectivity/network-ops/reading-network-state), hev 2.18.0 [configuration parser](https://github.com/heiher/hev-socks5-tunnel/blob/2.18.0/src/hev-config.c) and [combined TCP splicer](https://github.com/heiher/hev-socks5-tunnel/blob/2.18.0/src/hev-socks5-session-tcp.c). The pinned splicer processes both directions in one loop and yields when neither has data; native timeout value is kept at its existing default rather than disabling it.
